# Quarantined tests and gates (speed mode)

Adam approved speed mode on 2026-10-20: a known flaky test is skipped on CI,
with an issue link, instead of being rerun until it passes; and the benches'
display-link stall failures warn instead of failing the job. Everything below
is tracked in [#34](https://github.com/AdamAugustinsky/go-native-ui/issues/34).

How it works, in `.github/workflows/ci.yml`:

- A job with tests quarantined has a `QUARANTINE` regexp; its `go test` steps
  pass it as `-skip "$QUARANTINE"`. A test is skipped only on the jobs that list
  it. The macOS test job and the Windows test jobs have one; the Linux jobs run
  everything (an empty regexp would skip every test, so they have none).
- The bench steps named below run through `stallgate.sh`: when the bench fails
  with a display-link stall message (`bench stalled`, `bench timed out`,
  `no frame callbacks`, a spike timeout or a wrong count of measured frames),
  the step prints `::warning::quarantined ...` and succeeds. Every other
  failure (allocations on macOS, CPU budgets) still fails the step.

To quarantine a test, add its name to the job's `QUARANTINE` regexp in
`.github/workflows/ci.yml` (create the `env:` entry and the `-skip` flag if the
job has none) and a row here with the failing run. To un-quarantine one, delete
its name there and its row here.

## Fixed on p8-windows-flakes (2026-10-29)

Flakes of the hosted Windows jobs (windows-2025 amd64, windows-11-arm arm64)
seen on 2026-10-28 and 29, none quarantined. Each cause was read from its CI
log; where the log could not settle it, the test now says what it needs to.

- `TestReceiveAllocations` (app/ws, amd64, about one run in two): `102`-`124 allocations in the process over 9800 messages` (p8-webview2 40797829935, 40803324033, 40806585827, 40811975293, 40816023392). The 1 ms ticker paced 240-400 messages a second on the loaded runner, so the run took 25-42 s instead of 10, and the process's background allocations (the runtime's, about 3 a second) passed a budget of one per hundred messages. The paced run now profiles every allocation and counts those whose stack passes through the module's code outside a test file; the rest are reported. The network workflow's run had 15-18 of ours on Windows, 0-7 elsewhere, against 98 allowed.
- `TestWindowsRecordWindow`, `TestWindowsVideoOnlyScaled`, `TestWindowsDiscard`, `TestWindowsTargetGone`, `TestWindowsBusy` (media/capture): one recording whose capture thread fell behind (WriteSample waits for the software encoder on a loaded runner) failed, and the others followed with `a recording is already running`. Stop to Ended took 5.6-20 s; past the session's 15 s stop timeout the recording ended with the file not finalized (`80 bytes, 0 tracks`, 40797829935 attempt 2; `13602 bytes, 0 tracks` after 21.5 s, H2's 40823273045 attempt 2), and once it was still running after the test's 30 s (40797451836, 40808701648). A behind thread also wrote the frames up to the time it got to the stop, not the stop's: a 5 s recording made a 14.7 s file (40797829935 attempt 1). Fixed in the recorder: the stop stops its clock (`recorder.stopAt`). The live tests give the session 3 minutes to stop and wait up to 4 for Ended, and the recorder's trace now covers the finish (loop ended, last samples, finalized), which a recording that does not end reports.
- `TestFileDialogsCancelledOnceEach` (platform) is quarantined on the Windows jobs instead, with the other tests that show a file dialog (the table above).
- `TestHostFocusHandOffAndCommands` (platform): `focus into a host reported the window's focus change` (EvFocus gained, p8-windows-flakes 40825454957 arm64). The window did not have the focus when it handed it to the host (another process's window had the foreground), and gained it then. The test holds the activation and waits for the window's focus before the hand-off.
- `TestCloseStopsThePlacesWorker` (cmd/pilot/pilot): `3 probes started, want the first one blocked` (40825454957 arm64). The test's gate was opened by a 5 s safety timer before the check, on a runner whose first frame took that long; the timer is 60 s, and the first probe is waited for up to 10 s.
- `TestPostWithTableFullHasNoActions` (app/notify, fake center): `no result for ticket` (40816023392 amd64). The test waited for the note to reach the fake system, then read the post's result once, but the service delivers the result after the note. `resultOf` now waits for it, for every caller.
- `TestEditorCompletionAndHostCommands` (platform; fails without H2 too): `completion commands []` (40805350430, 40816023392, amd64). The editor's WM_KILLFOCUS ends a completion, so another process's window taking the foreground turns the keys that follow into plain keys. The test holds the `activation` lock, as the tests that take the foreground do, and tries again (up to three times) only when the editor reports the completion cancelled by a focus loss.
- `TestEditorDrawsColourEmoji` (platform): `yellow pixels: 0 (frames presented 2)` (40806585827 arm64). The window was read once 300 ms after the present; DWM's composition comes later on a loaded runner. It is read again, pumping, until the emoji shows (10 s at most).
- `TestRequestPasteWaitsForABusyClipboard`, `TestRequestPasteFailsWhenTheClipboardStaysBusy`, `TestSetClipboardTextWaitsForABusyClipboard` (platform): no answer within 1 or 2 s, or a worker not back within 1 s (40811975293, 40816023392, 40805350430). No other test process uses the system clipboard (every other package's tests use a rig's), so these were the runner's load on the worker's 2 ms retries and the UI thread's Waits. The waits are up to 5 s (10 s for the worker's return), the properties are kept (the answer is not failed, and comes within the paste's own limit, which a Wait the answer did not wake would overrun), and a failure now names which window, of which process, has the clipboard open and owns it.
- `TestPackageWithoutAppleIdentity` (cmd/gnui) is a macOS one: `hdiutil verify` failed with EAGAIN through gnui's 20 s of retries (40811975293 attempt 1). app/selfupdate's HFS+ tests keep an image attached in another process meanwhile. Both now hold a `diskimage` lock.
- `TestViewMatrix` on Windows arm64 (`the page on screen: not within 10s`, 40803324033) is H2's (app/webview); H2 landed with app/webview running alone in its own Windows step (a91c3594), which this branch keeps.

## Fixed on p8-macos-flakes (2026-10-29)

Flakes of the hosted macOS job that were never quarantined, each with the
cause found in its CI log and fixed in the test:

- `TestViewMatrix` (app/webview), idle gate: `an idle view drew 1 frames in 3 s` with no app event (p8-win-dialogs 40805350430). The frame was the one owed by the test's own Do before the 3 s, drawn more than 500 ms late because a covered window's frames come late; it failed the same way 3 of 3 times on the Mac mini (display asleep). The gate now waits for that frame, and counts only frames whose debug-overlay causes are not the system's (`widgettest.FramesSince`). 20 of 20 separate runs passed on the Mac mini.
- `TestViewMatrix`, popups: `the title Popup: not within 20s` (p8-win-panels 40792692726 attempt 1). The page opens `/b` in place 50 ms after it loads, so a poll on a loaded runner first sees Page B; the in-place view now waits only for Page B.
- `TestVideoInWindowVisibilityChanges` (media): `paused window visibility did not settle` or `paused: 1 frames in a visibility-stable second` (6 runs on 2026-10-28 and 29, e.g. 40805350430, 40791826821, 40808701648). Other test processes' windows covered and uncovered it every second (its state line shows it); the single extra frame is most likely the one owed by the test's earlier Do (defineLater), which a covered window draws late, as in `TestViewMatrix`. The paused check now counts frames by their recorded causes instead of waiting for the visibility to hold still.
- `TestVideoPlaysOnInAHiddenWindow` (media), un-quarantined (quarantined 2026-10-28, faf75ea8): `hidden and playing: 3 frames built, 0 drew the video; want none` (2 allowed; p9-integrate 40713484538, p9-ship 40725995275). On the Mac mini it failed 3 of 3 with 144 frames that all drew the video. The cause is in platform: AppKit reports an occlusion change only when the state changes, so a window never reported visible (opened covered, or on an asleep display) was ordered out by `Hide` with no event, and the app drew on unpaced without `Input.Hidden`. `Hide` now reports such a window hidden and `Show` takes it back. The test counts the frames by cause from after the hiding Do's own frame and lists them. Locally 20 of 20 after the fix.
- `TestVideoFrames` (media, offscreen: no window, so no frame causes): `paused at 1.614s, then at 1.806s` (p8-win-gaps 40825237562) and `paused at 2.33s: left [16 235 6], want [0 0 255]` (40723321723). AVPlayer's clock ran on for a moment after Pause returned on the loaded runner, and frames were pulled late, so the frame held was the previous second's. The test reads the position once it has stopped (within 400 ms of Pause) and checks that the frame held is the one showing when it paused.
- `TestPlayerPauseNearEnd` (media): `resumed at 971ms: ended after 425ms, want about 28ms` (40805350430 attempt 1). The end after resuming is the late-end case `endedOnTime` already remeasures for `TestPlayerSeekAndPause` (264-490 ms late on a loaded runner); it now uses it.

## Un-quarantined on p9-ci-flakes

Each was skipped on some job and now runs on all of them. "Passes" counts CI
runs of this branch (the macOS and Windows test jobs, the four Linux jobs); a
test that fails again on main goes back in.

Runs: R1 [40633691026](https://github.com/AdamAugustinsky/go-native-ui/actions/runs/40633691026) (all 11 jobs green), R2 [40635284542](https://github.com/AdamAugustinsky/go-native-ui/actions/runs/40635284542) (all green but macOS, which failed `TestPackageAppMustMatchItsConfig`, a test that was not quarantined and a flake of its own: see the last item), R3 [40638991672](https://github.com/AdamAugustinsky/go-native-ui/actions/runs/40638991672) (all 11 jobs green, with the fix to that test).

**The cause is found and fixed** (a test that fails without the fix is named):

- `TestColdThreadAttach`, `TestZeroAlloc` (internal/ffi, Linux): not ffi at all. Profiling every allocation (`MemProfileRate = 1`, a Linux container) put the one 16 or 32 byte object in `runtime.(*scavengerState).sleep` → `(*timers).addHeap`: the scavenger sleeps on a timer in the heap of whichever P it last ran on, and the first time a P's heap grows is an append. The tests give every P's timer heap room before they count (564153d); 3 of 300 runs counted it before and 0 of 1100 after on arm64, 3 of 300 and 0 of 300 on amd64 (emulated). A rarer window of 7 or 8 objects is a new thread's M, which the tests' three windows take.
- `TestEvictionSkipsReplacedNotes` (app/notify, Windows): the oldest note was chosen by its post time in ns, and Windows' clock ticks about every 0.5 ms or more, so two posts could tie and the lower slot won (`evicted n0,x`). Ties go to the smaller gen (0d96655); `TestEvictionSkipsReplacedNotesOnACoarseClock` freezes the clock and fails without it with the same message.
- `TestLastDrainEndsParking` (app/notify, Linux): the retry goroutine ends its list before it answers what it stored, so the last drain, seeing it not running, returned before the answer. It waits for the goroutine whenever one was started (0d96655); `TestLastDrainWaitsForTheAnswerOfTheRetry` fails without it. The CI log of the original failure is gone; this is the race the code has, not a reproduction of that failure.
- `TestCloseDoesNotWaitForTheIconStyleRead`, `TestOffscreenRunsLeaveNoWorkersOrHandles` (cmd/pilot/pilot, Windows): clock races (a read released by a 5 s timer, a Close over 1 s that includes the icon cache's second, workers given 2 s to end). Close runs under a 10 s deadline, workers get 30 s (e9fada7).
- `TestPackagedBinaryHasNoDebugChordOrInspector` (cmd/gnui, Windows, Linux): the darwin build fetched purego from the proxy and got a stream error. It builds with `GOPROXY=off`; the jobs run `go mod download`; off CI it skips when the modules are not cached (b7a6d50).
- `TestDragTypesDoNotReachHosts` (platform, macOS): registered a host for `arrText` before `dragInit` had made it; alone, it failed every time (reproduced locally). It calls `dragInit` first.
- `TestOtherWindows` (widget/widgettest/live, macOS): waits up to 240 frames for the key instead of three, and a cleanup closes its window whatever way it ends, so a failure no longer breaks the next test. The key's not moving was not reproduced.
- `TestPackageAppMustMatchItsConfig` (cmd/gnui, macOS; never quarantined): `checkBuiltApp` ranged over a map, so it named the version before the identifier one time in eight (6 of 80 runs locally, R2 on CI). Fixed order.

**Un-quarantined without a cause found**: the test passed in CI and the part that could be checked locally was hardened or read, but nothing reproduced the original failure, so these are the ones to put back first if they fail on main.

- `TestMixFollowsAndDoesNotAllocate` (theme, macOS and Linux): `AllocsPerRun(100)` divides as integers, so "allocates 1 times" meant 100 or more allocations in the window, which the code cannot make (0 of 2000 runs in Linux containers). It takes the quietest of three windows and reports all three.
- `TestSystemIconsWindowsConcurrent` (img, Windows): the failing step is traced and logged by the test (`failed decode steps`). It passed on both Windows jobs in each run. No COM race was found by reading `sysicon_windows.go` either.
- `TestPackageWithoutAppleIdentity` (cmd/gnui, macOS): the hdiutil race is retried in `gnui` since a5a206e.
- `TestEditorNestedLoopDraws`, `TestEditorUndoRedo`, `TestEditorMarkedTextSubmission`, `TestStallOfAHiddenWindowSkipsAndSaysWhy`, `TestRunKeepsDesignatedRequirement`, `TestScrollEventsThroughTheQueue`, `TestVListEditFrameBudget` (macOS): they failed "under contention" or about one run in five before the benches moved to their own job; they passed on the macOS test job in R2 and R3 and passed repeatedly where they could be run here (`TestScrollEventsThroughTheQueue` 300 of 300, `TestRunKeepsDesignatedRequirement` 10 of 10, `TestVListEditFrameBudget` 5 of 5). Two CI runs of a test that failed one in five is weak evidence.
